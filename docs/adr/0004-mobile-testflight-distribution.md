# 0004 — Mobile TestFlight Distribution

## Status

Accepted (2026-06-03).

## Context

ADR 0003 stood up a staging backend on Fly (`sitetracker-backend-staging`,
`syd`) but explicitly deferred the iOS distribution pipeline to its own
slice. The first real-user trial needs the SiteTracker app installable on a
physical iPhone and working over cellular with the operator's PC off — which
the LAN dev-server setup cannot do. The mobile app resolves its API base from
`EXPO_PUBLIC_API_URL` at build time and silently falls back to
`http://127.0.0.1:8000` when that variable is unset
(`mobile/src/api/client.ts`), so the distribution config must make the
staging URL deterministic. Constraints are unchanged from ADR 0003: one AU
residential builder, a 1–2 person operator team, no DevOps headcount,
iOS-first.

## Decision

- **Build service.** EAS Build (cloud). No local Xcode/macOS required; iOS
  signing credentials are EAS-managed.
- **Submit path.** EAS Submit uploads the store-distribution build to App
  Store Connect, which feeds Apple TestFlight.
- **Distribution terms are kept distinct** (they are not interchangeable):
  - *EAS internal distribution build* — an installable build delivered
    through EAS using ad-hoc provisioning; NOT TestFlight. Optional, via the
    `preview` profile in `mobile/eas.json`.
  - *Apple TestFlight internal testing* — testers are App Store Connect users
    (≤100); builds do not require Beta App Review.
  - *Apple TestFlight external testing* — up to 10,000 testers; the first
    build sent to an external group requires Apple Beta App Review.
- **First path.** Apple TestFlight **internal** testing, operator only — valid
  only if the operator's Apple account is an App Store Connect user.
  Company-internal staff (e.g. a site worker or family member) who are not App
  Store Connect users are Apple **external** testers and may trigger Beta App
  Review; that flow is not opened until the operator's own install passes.
- **API base URL.** Staging `https://sitetracker-backend-staging.fly.dev`,
  injected via the EAS build-profile `env.EXPO_PUBLIC_API_URL` in
  `mobile/eas.json` only — never hard-coded in app source, never read from a
  gitignored dotenv at cloud-build time. No `EXPO_PUBLIC_*` value is ever a
  secret.
- **Identity & versioning.** Bundle id `com.sitetracker.mobile` (unchanged);
  build numbers are EAS-managed (`cli.appVersionSource = remote`,
  `production.autoIncrement`); the EAS `projectId` is generated by `eas init`
  (operator), never hand-written.
- **Scope.** Staging-pointed internal trial only. No production endpoint, no
  external testers yet, no CI/CD, no OTA / EAS Update, no new app features.

## Consequences

- The API URL is frozen into each build; changing it needs a rebuild. A
  pre-build backend-liveness gate and a post-build config check are mandatory
  (`docs/operations/testflight-build.md`).
- The operator holds every Apple/Expo credential; the assistant never handles
  enrollment, signing, the App Store Connect API key, or an Expo token.
- Adding non-ASC company staff later means external testing and, for the first
  external build, Apple Beta App Review.
- Secrets never live in `EXPO_PUBLIC_*` or any committed file; the staging URL
  is public and safe to commit. Auth stays runtime JWT.
- Complements ADR 0002 (env/secrets) and ADR 0003 (staging deployment);
  supersedes nothing. A production distribution decision is a later ADR.
